# 「软件取不到电话号码」的根因诊断报告

> 2026-10-07 · 只做诊断取证，**未改任何业务代码、未动生产数据**

---

## 结论速览

不是"缺方法"，是**四个独立问题叠在一起**。其中两个是真 bug，一个是最可能的元凶，一个是正常的隐私机制。

| # | 问题                                        | 性质    | 严重度   |
| - | ----------------------------------------- | ----- | ----- |
| 1 | `withTimeout` 超时后**丢弃已拿到的号码**             | 真 bug | 🔴 最高 |
| 2 | `msg.author` 带 `:4` 设备后缀没剥，**同客户被拆成两个档案** | 真 bug | 🔴 高  |
| 3 | 底层本来就只给 LID（过滤链没错，是上游无数据）                 | 机制    | 🟡 中  |
| 4 | 1A00012 的号码是**人工填的**，不是 bug               | 排除项   | ⚪ 不动  |

---

## 根因 1 🔴 超时后号码被白扔（最可能的元凶）

`src/identity.js:439`

```js
function withTimeout(p, ms, label = '') {
  return Promise.race([
    Promise.resolve(p),
    new Promise((_, rej) => setTimeout(() => rej(new Error(`${label}超时`)), ms)),
  ]);
}
```

**`Promise.race` 只是"不再等"，不是"取消"。**  
底层那个 `getContactLidAndPhone()` / `pupPage.evaluate()` **仍然在浏览器里继续跑**，  
几秒后拿到号码时，结果被丢在 `identity.js:289` 和 `:299` 的局部变量里——**没人接、也没写缓存**。

而 `CONTACT_TIMEOUT = 8000`（8 秒）对 `queryWidExists` 这种真实网络往返**偏短**。

**后果：号码"其实拿到了"，但被当成失败扔掉。**&#x8FD9;完全符合你说的"还是无法获取"——  
因为它不是拿不到，是拿到了没人要。

### 修法

1. 超时从 8s 放宽到 20s；
2. 迟到回来的结果**照样落缓存**（用 `.then(v => ({ ok: v }))` 参与竞速，而不是裸 `race`）。

## 根因 2 🔴 同一个客户被拆成两个档案

生产库实证：

| 编号      | wa_jid                 | 号码 |
| ------- | ---------------------- | -- |
| 1A00011 | `93042480525348:4@lid` | 空  |
| 1A00014 | `93042480525348:5@lid` | 空  |

**前缀完全相同**，只是设备后缀不同（`:4` / `:5`），却被当成两个不同客户建了档。

**为什么**：`getOrCreateCustomer`（`db.js:192`）用 `WHERE wa_jid=?` 精确匹配，  
**而 `jidOfMessage`（`identity.js:237`）取 `msg.author` 时从不剥 `:N` 后缀**。

**后果**：号码查了两次都查不到（两个错误 ID 都不是真实 LID），两个档案都是空的。  
库里 2 条含冒号的 jid，**就是这个问题**。

### 修法

`jidOfMessage` 规范化：剥掉 `:N` 后缀（`/:\d+$/`），并对已有数据做一次性归并。

## 根因 3🟡 底层本来就只给 LID（这部分是机制，不是 bug）

我穷举了 7 种底层返回组合跑 `phoneFromContact`，验证你的过滤链**逻辑完全正确**：

| 底层返回                             | 结果     |
| -------------------------------- | ------ |
| `id` 被注入层换成真号                    | ✅ 取到   |
| `id` 是 @lid，但 `number` 是真号       | ✅ 取到   |
| `id` 是 @lid，`number` 也是那串 LID    | ❌ 正确拦下 |
| `id` 是 @lid，`number` 空/undefined | ❌ 空    |

这与 wwjs 源码 `Utils.js:1014` 完全吻合：

```js
if (wid.isLid() && contact.phoneNumber) { res.id = contact.phoneNumber; }
```

**`contact.phoneNumber` 为空时，`id` 和 `number` 会同时是那串 LID。**

**→ 所以不是被你的校验误杀，是 WhatsApp 真的没给号码。**

## 根因 4 ⚪ 1A00012 不是 bug（别动它）

`1A00012` 的 `phone = +12104878552`，`created_at_source = **manual**`。

**这是人工填进去的**，不是程序存错的。而且 `isLidPhone` 的判据是  
"jid 是 @lid **且**号码 ≥14 位"才拦，11 位不触发阈值。

→ **`isLidPhone` 没有漏网，这行数据是干净的。不要动它。**

---

## 🔴 必须先接受的现实上限

**纯陌生人的手机号，服务端就没有，WhatsApp 不会给。** 这是 LID 隐私保护机制本身。

| 客户关系              | 能不能解          |
| ----------------- | ------------- |
| 在你通讯录里 / 曾互加过     | ✅ 能           |
| 共同群成员             | ✅ 能           |
| 对方发过名片式分享         | ✅ 能           |
| **纯陌生人，没存你、无共同群** | ❌ **服务端也拿不到** |

库里 4 条 `@lid`，其中 2 条还是同客户被拆开的，实际只有 **3 个不同客户**。  
**这 3 个里能救几个，不跑诊断谁也说不准。**
